  <action>
    1. Add `pub mod phase_runner;` to lib.rs.

    2. Create crates/ath-orchestrator/src/phase_runner.rs:

    Define zero-sized state marker structs: Pending, Running, AwaitingReview, Complete, ReviewFailed, Retrying.

    Define PhaseState<S> with fields: phase_id (u32), phase_name (String), _state (PhantomData<S>), and state-specific data:
    - For AwaitingReview: store TaskOutputs (Vec<TaskOutput>) and attempt_number (u32)
    - For Retrying: store attempt_number (u32) and feedback (ReviewVerdict)
    - For ReviewFailed: store attempts (u32) and final_reason (String)
    - Use separate concrete structs for state-specific data to avoid generic proliferation

    Implement transitions as consuming methods:
    - PhaseState<Pending>::start(self) -> PhaseState<Running>
    - PhaseState<Running>::submit_for_review(self, outputs: Vec<TaskOutput>, attempt: u32) -> PhaseState<AwaitingReview>
    - PhaseState<AwaitingReview>::approve(self) -> PhaseState<Complete>
    - PhaseState<AwaitingReview>::reject(self, verdict: ReviewVerdict) -> RejectOutcome
      where RejectOutcome is enum { Retry(PhaseState<Retrying>), Failed(PhaseState<ReviewFailed>) }
      Logic: if attempt_number < 3 -> Retry with attempt_number, else Failed
    - PhaseState<Retrying>::retry(self) -> PhaseState<Running>

    Define PhaseStatus enum (serializable, for logging/PhaseRecord):
    - Pending, Running, AwaitingReview, Complete, ReviewFailed { attempts: u32, final_reason: String }, Retrying { attempt_number: u32 }

    Define TaskOutput struct: task_name (String), agent (AgentKind), files_produced (Vec<FileOutput>), explanation (String), issues_encountered (Vec<String>), input_tokens (u64), output_tokens (u64).

    Define FileOutput struct: path (String), content (String).

    Add task_output_schema() -> serde_json::Value function returning the JSON schema for structured output (as shown in RESEARCH.md).

    All structs derive Debug, Clone, Serialize, Deserialize, PartialEq as appropriate. State markers only need Debug.

    Per user decision: use PhantomData typestate for transitions, PhaseStatus enum for serialization/logging. Typestate is internal to the execution loop; external code uses PhaseStatus.

    Per user decision: attempt numbering is 1-based. Attempt 1 = first try. Max = 3. Retrying carries the NEXT attempt number (2 or 3).
